PART 1 — DESIGN AND TECHNOLOGY NOTE (maximum 200 words)

I organised Crystal’s ecosystem around one idea: building a better human experience. Three themes—spaces and objects, ideas and learning, people and possibility—help visitors understand the relationships between the initiatives before choosing a destination.

The page introduces Crystal first, then connects her purpose to her ecosystem, demonstrates it through selected work, and ends with clear routes for project clients, event organisers and collaborators. Research and writing sit directly under her personal brand rather than becoming another competing business.

Warm neutrals, forest green, editorial typography and the supplied portraits create a calm, distinctive identity. Project concepts are labelled honestly. Missing initiative links lead to contextual information and Crystal’s verified LinkedIn profile rather than invented destinations.

I chose semantic HTML, responsive CSS and small vanilla JavaScript interactions because this single-page experience does not need a framework. Local fonts, compressed WebP images and deferred JavaScript keep dependencies and network overhead low. The site includes keyboard navigation, native modal dialogs, visible focus states, responsive layouts and reduced-motion support.

The contact flow helps visitors draft and copy a message; it clearly explains that delivery happens through LinkedIn. No enquiry submission or data collection is simulated.

PART 2 — AI PRODUCT THINKING (maximum 300 words)

TEA Practice Companion would help early-career architects turn a professional question into a practical learning plan grounded in The Effective Architect’s approved teaching materials.

Its audience is students and emerging architects who struggle to connect scattered advice to a specific career task: preparing a portfolio, understanding a project workflow or planning professional development.

A user chooses a goal and experience level, then asks a question such as “How should I structure my first residential portfolio?” The tool returns a short action plan, links to relevant TEA lessons, and questions for reflection. Every factual teaching claim must cite an approved source. If the library cannot support an answer, the tool says so and suggests a human mentor.

I would use the Gemini API with its File Search retrieval tool. It can index a curated document library and retrieve relevant passages for a model response, reducing the need to build a separate retrieval service for the prototype. I would benchmark an available Flash model on accuracy, latency and cost before pinning a version.

The first version would contain 20 reviewed TEA resources, a simple web interface and a server endpoint that keeps the API key private. It would support one task at a time and return structured actions and citations. Before a small pilot, I would test 50 representative questions with an architect, including unsupported questions and malicious instructions embedded in documents.

Safeguards include source verification, rate limits, cost caps and no user-uploaded project files initially. It must never approve structural decisions, code compliance or construction safety. Users should not submit confidential client data. Success means users find the right resource and complete a useful next action—not simply generate more messages.

PART 3 — ANALYTICS & IMPROVEMENT (maximum 250 words)

I would measure whether visitors reach a useful destination: an initiative, a project conversation, a speaking invitation or a learning resource. I would track acquisition source, device, engaged visits, initiative selections, outbound clicks and contact starts. For a future enquiry form, I would measure starts, validation failures and server-confirmed successful submissions. A LinkedIn click or copied message is a handoff, not a confirmed enquiry.

I would use GA4 for event funnels, Search Console for search visibility, and PageSpeed Insights plus real-user Core Web Vitals for performance. Consent-aware, masked session recordings could help explain friction without capturing message content. Reports would distinguish qualified enquiries from raw traffic.

Five enquiries from 5,000 visitors is a 0.1% visitor-to-enquiry rate. I would first verify the denominator, remove bot and internal traffic, and confirm that all genuine submissions are counted and delivered. A low rate alone does not establish the cause.

Next, I would segment by channel, landing page and device. Are visitors potential clients? Does the page clearly explain the offer? Can they find credible work and a relevant next step? Do mobile errors, slow loading or a lengthy form interrupt the journey?

I would combine funnel drop-offs with a few usability sessions, fix delivery or usability defects first, and test one evidence-backed change at a time. With only five conversions, I would avoid declaring an A/B-test winner prematurely and observe a longer period, lead quality and upstream engagement.
